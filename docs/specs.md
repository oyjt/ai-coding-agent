# Spec 设计

## 1. Spec 是什么

Spec 是具体任务的**需求规格与验收契约**，回答：

> 这次到底要实现什么？

Spec 不负责描述详细实现方案。

## 2. Spec、Plan、Code、Verification

```text
Spec
 ↓
要实现什么
 ↓
Plan
 ↓
怎么实现
 ↓
Code
 ↓
实际实现
 ↓
Verification
 ↓
是否满足 Spec
```

## 3. 什么时候需要 Spec

| 任务等级 | 要求 |
| --- | --- |
| S | 不需要 |
| M | 可选 |
| L | 必须 |
| CRITICAL | 必须 |

M 级如果存在多个合理解释、跨共享模块、影响范围较大或风险较高，应主动创建 Spec。

## 4. Spec 内容

模板位于：

```text
templates/project/.aca/specs/SPEC.md
```

至少包含：

- 任务级别
- 背景与目标
- 需求范围
- 非目标
- 影响范围
- 验收标准
- 验证方式

L 级建议增加风险和回滚方案；CRITICAL 级必须明确风险、回滚和安全要求。

## 5. 验收标准

验收标准应该是可验证的，而不是模糊描述。

不推荐：

```text
- 登录功能体验良好
```

推荐：

```text
- [ ] 手机号格式错误时阻止提交
- [ ] 验证码发送成功后显示倒计时
- [ ] 验证码错误时显示错误提示
- [ ] 登录成功后进入首页
```

## 6. 生命周期

当前项目不实现复杂状态机，但建议任务按以下逻辑推进：

```text
created
  ↓
planned
  ↓
implementing
  ↓
reviewing
  ↓
verified
  ↓
completed
```

这些状态目前属于工作约定，不要求在代码中建立独立状态引擎。

## 7. 简单任务不强制 Spec

不要为了形式让所有任务都生成 Spec。

例如：

```text
“把按钮文案从提交改成保存”
```

属于 S 级任务，可以直接修改并执行必要验证。

Spec 的价值在于减少复杂任务的需求歧义，而不是增加文件数量。
